# Decisions

Short record of what was decided and why, so any future session (mine or Claude Code's) can catch up without rereading everything. One or two lines each. Newest at the bottom.

## v1 data model and scope (July 8, 2026)

- One table, not two. Internships and scholarships share a single `applications` table with a `type` discriminator column. Reason: the subtypes differ by data, not behavior, and the whole point is one unified pipeline. Two tables would double the work for every feature. Revisit only if a subtype ever needs genuinely different processing.
- Types for v1: internship and scholarship only. Fellowship, research, and grant get added when I actually apply to one. Not modeling hypotheticals.
- Queryable fields are real columns; display only fields go in a JSON column. Anything I filter, sort, or search by (deadline, status, type, priority, organization, role_or_program) is a real typed column. Messy or evolving parser output goes in a `jd_parsed` JSON blob. Promote a JSON field to a real column the day I actually filter on it, which is a one column migration.
- No money columns yet. Salary and award amount live in `jd_parsed` for now. Promote to a column when I actually want to sort by money, not before.
- One shared status enum, superset of both types. Values (14, trimmed from the original 16): discovered, drafting, ready, applied, recruiter_engaged, phone_screen, technical_interview, onsite, offer, accepted, declined, rejected, ghosted, missed_deadline. No transition validation in v1; that state machine is deferred to v2.
  - Dropped `shortlisted` (July 10, 2026): overlaps with what `priority` already expresses ("real target" = priority high). Re-add if a distinct vetted-but-not-drafting state proves useful.
  - Dropped `applied_confirmed` (July 10, 2026): the applied-vs-confirmed gap only earns its keep in v4 when the n8n Gmail watcher auto-flips it on a receipt email. Maintaining it by hand in v1 is busywork. Re-add with that automation.
- Hard delete for v1. Single careful user. Add soft delete only if I fat finger a row and regret it.
- UUID primary keys stored as VARCHAR(36). Reason: IDs don't leak how many applications I have and don't collide if n8n ever creates rows. Cost is uglier URLs, acceptable.
- created_at and updated_at timestamps from the start. Cheap, and I'll want "added this week" and "stale 30 days" later.
- SQLite for v1. Postgres later, only when I deploy for real and need concurrency or pgvector.
- Build order: CRUD loop first (create, read, update, list by hand), JD parsing and AI second. One unknown at a time.
- Deferred on purpose, do not build yet: resume_versions table (v2), timeline_events table (v4), essays table and pgvector (v6 or never), match scoring, materials checklist, contacts, deployment, auth. These arrive with the version that owns them.

## v1 skeleton (July 8, 2026)

- No config.py in v1. DATABASE_URL is a hardcoded constant in `database.py` (`sqlite:///./data/dev.db`). Reason: v1 CRUD reads no secrets or env vars, so pydantic-settings earns its place only in v2 (JD parsing API key). Adding it now is scaffolding for scaffolding.
- venv is path-locked. A Python virtualenv hardcodes its absolute path into console scripts (uvicorn, pip, alembic) and symlinks, so moving the project folder breaks it (symptom: "bad interpreter: .../no such file or directory"). Fix: `cd backend && rm -rf .venv && ~/.local/bin/uv venv && source .venv/bin/activate && uv pip install fastapi uvicorn sqlalchemy alembic`. The .venv is gitignored build state, safe to delete and rebuild.

## v1 Application model + Alembic (July 10, 2026)

- Status enum trimmed to 14 (see above): dropped `shortlisted` and `applied_confirmed`.
- Alembic `env.py` uses `DATABASE_URL` imported from `database.py` as the single source of truth, not a second URL hardcoded in `alembic.ini`. Model is imported in env.py purely to register its table on `Base.metadata` (autogenerate sees nothing without it).
- `render_as_batch=True` set in env.py. Reason: SQLite can't real-ALTER columns; batch mode makes Alembic emulate ALTER by copy-and-swap. Not needed for the initial create, but v2 column adds would break without it.
- First migration `5a510583d8ee` creates the applications table. The stale dev.db from the pre-rebuild build (1 test row: CareDX internship, notes="string", old `top_target` priority, extra jd_text/match_score columns) was deleted and rebuilt fresh. Backup lives in the session scratchpad, not the repo.

## v1 CRUD: schemas, services, routes, tests (July 12, 2026)

- Pydantic schemas split by operation: `ApplicationBase` holds the shared human-set fields, with `Create`/`Update`/`Read` on top. `Create` allows `status` and `priority` (optional-with-default) so a row can be added already-applied or high-priority. `Update` is standalone with every field optional (partial PATCH). `jd_parsed` is read-only: in `Read`, absent from `Create`/`Update` since no parser exists in v1.
- Layering: routes stay thin (validate, call service, return); all DB logic lives in `services/`. Not-found handling chose "Option A": services return `Application | None`, routes raise `HTTPException(404)`. Keeps services HTTP-ignorant so a non-HTTP caller (n8n, tests) can reuse them.
- Sessions: services never open or close a session; `get_db` via `Depends()` owns the lifecycle. That decoupling is also what lets a test pass an in-memory session straight into a service.
- Update uses `model_dump(exclude_unset=True)` + a `setattr` loop so only fields the client actually sent are changed; unsent fields are never overwritten. No `db.add` on update (the fetched row is already session-tracked, so commit flushes the dirty changes). Delete returns 204 No Content.
- Tests: in-memory SQLite fixture in `tests/conftest.py` using `StaticPool` (one shared connection, or the `:memory:` tables vanish between connections). Service-level tests only, no route/TestClient tests in v1 (curl covers the HTTP layer by hand). First service function was written test-first; the update test specifically asserts unsent fields stay unchanged, guarding the `exclude_unset` behavior.

## v1 frontend: shell, list, CRUD UI (July 12, 2026)

- Stack in build: Vite + React 19 + TypeScript (strict) + Tailwind v4. Tailwind v4 is CSS-first (no `tailwind.config.js`); design tokens live in an `@theme` block in `frontend/src/index.css`, the single source of truth for the visual system. Utilities generate from token names (`--color-surface` becomes `bg-surface`).
- Scope discipline: built only what the v1 API backs. Omitted the mockup's summary cards, the sidebar pipeline counts, and the per-row location line (no location column exists). Future nav (Deadlines, Organizations, Documents, Analytics) renders disabled and tagged "Soon", never with invented counts. Promote any of these the day real data backs them.
- Display mappings live in `lib/format.ts`: `internship` shows as "Job", `scholarship` as-is; statuses shown granular and humanized ("Technical interview"), not collapsed into buckets, so a badge never misrepresents a row.
- Visual direction is in `docs/design.md` and the tokens, but polish is deliberately deferred (revamp later), function first. Purple stays scarce: primary action, active nav, selected row, focused input, links, and the offer badge, nowhere else.
- Data fetch is lifted to `App` via a `useApplications` hook so the sidebar count and the table share one fetch, not two. After any write the list refreshes via `refetch()`. Optimistic update (append locally, skip the round trip) is deferred, flagged as a LATER comment in the hook.
- One modal, `ApplicationFormModal`, serves both create and edit, switched by an optional `application` prop, so the eight fields exist once. Delete lives inside it in edit mode behind a `window.confirm` (v1 is hard delete, no undo). Clicking a row opens the edit modal pre-filled.
- HTTP is wrapped in `lib/api.ts` (list/create/update/delete); components never call `fetch` directly. `lib/types.ts` mirrors the backend Pydantic schemas by hand (manual sync in v1).
- Dev proxy: Vite rewrites `/api/*` to `http://localhost:8000/*`, stripping the `/api` prefix, because the backend serves routes without one. Frontend code always calls `/api/...`.
- v1 CRUD is now complete through the UI (create, read, update, delete). Next unknown, per the build-order rule, is v2: JD/URL parsing via the Claude API.

## v2 JD parsing: paste-text extraction (July 20, 2026)

- Scope: paste JD **text**, not a URL. URL fetching is deferred — LinkedIn, Greenhouse, and Workday postings are JavaScript-rendered or bot-blocked, so a plain HTTP GET returns a login wall, not the posting. Parsing pasted text is the valuable core; URL fetch is a separate, flaky subproblem for a later pass.
- `config.py` finally exists, using pydantic-settings, exactly as the v1-skeleton note predicted ("pydantic-settings earns its place only in v2"). v1 read no secrets; v2's `ANTHROPIC_API_KEY` is the first. `Settings` holds `anthropic_api_key` (required, no default so the app won't start without it) and `anthropic_model` (default `claude-haiku-4-5`, a tunable so the model swaps without code changes). `get_settings()` is an `@lru_cache` singleton injected via `Depends`, mirroring `get_db`.
- Model: `claude-haiku-4-5`, per vision's "cheaper capable model for parsing and routine work." Verified current against the API docs. One-line bump to `claude-sonnet-5` via the setting if extraction quality on a messy posting disappoints.
- Extraction method: **structured outputs** (`client.messages.parse(output_format=ParsedJob)`), not tool use. For pure "give me typed data back" extraction it's cleaner than forcing a tool call, and it fits the Pydantic-everywhere convention. Caveat that shaped the schema: structured outputs rejects length/number constraints, so `ParsedJob` fields stay plain-typed (no `Field(min_length=...)`).
- Two schemas, deliberately separate: `ParsedJob` is the AI's output shape (content); `ApplicationCreate` is the DB shape (structure). Same content-vs-format split as the resume design. Mapping between them is a distinct concern, kept out of the parser so parsing stays single-responsibility.
- `POST /applications/parse` returns a raw `ParsedJob` and never writes a row (hard rule #1: never auto-submit). It does **not** map to `ApplicationCreate`: `posting_url` is required on create and a pasted JD carries no URL, so the frontend pre-fills what it can and you add the URL and review before saving.
- Extras (`salary`, `location`, `summary`, `key_requirements`) are bundled into the `jd_parsed` column on create (done same session). This reverses the one v1 schema decision that mattered here: `jd_parsed` moves from read-only to settable on `ApplicationCreate`, now that a parser exists to fill it. `ApplicationUpdate` still omits it and `ApplicationBase` still excludes it (it's not a human-typed field). The autofill flow stashes the extras and sends them only on create; edit never touches the stored blob. Choice: store only the non-column extras, not the whole `ParsedJob` (org/role/deadline are already columns — no duplication). No UI to view `jd_parsed` yet — it's stored for later (resume-tailoring context, a future detail view).
- Tests mock the Anthropic client (`patch("services.parsing.Anthropic")`). The service calls a paid, non-deterministic API, so the same "tests never touch external state" rule that gave us the in-memory DB now keeps the suite off the network. The real call is verified by hand against a live posting.
- Frontend: an "Autofill from a posting" paste box lives **inside the create modal** (create mode only), not a second button/modal — least new surface, and it keeps the human-in-the-loop review inside the flow that already exists. It fills type/organization/role_or_program/deadline; purple stays reserved for Save, so Autofill is a grey secondary action.

## v2 resume tailoring: renderer choice (July 21, 2026)

- Renderer is WeasyPrint (HTML/CSS to PDF), chosen over ReportLab (pure Python) and Typst (new language). Reason: reuses the Tailwind/CSS knowledge already in play, and a locked Jinja HTML template plus a CSS file is the cleanest expression of the content vs format split (Claude edits YAML only, never sees the CSS). Cost accepted: a system dependency.
- System dependency: WeasyPrint needs the Pango and Cairo C libraries installed at the OS level (they do the actual text and shape drawing). On macOS: `brew install pango` (pulls in cairo and friends). This is not a pip/uv package, so a fresh machine or CI runner needs the brew install before `weasyprint` imports. Note for when v3 deployment arrives: the DigitalOcean droplet needs the equivalent apt packages (`libpango-1.0-0 libpangocairo-1.0-0`).
- macOS loader gotcha (hit and fixed July 21, 2026): after `brew install pango`, `import weasyprint` still failed with `OSError: cannot load library 'libgobject-2.0-0'`. Cause: Homebrew puts the libs in `/opt/homebrew/lib`, which macOS's dynamic loader does not search by default, and `DYLD_*` env vars must be set before the Python process launches (they can't be set from inside the app). Fix: appended `export DYLD_FALLBACK_LIBRARY_PATH="/opt/homebrew/lib:..."` to `backend/.venv/bin/activate`, so any `source .venv/bin/activate` (which every run command already does) resolves it. Caveat: the `.venv` is gitignored and rebuildable, so re-add this line after a venv rebuild (or put the export in your shell profile instead). Not needed on Linux/the droplet — apt installs libs to standard search paths.
- macOS `DYLD` purge + the DURABLE WeasyPrint fix (July 21, 2026): the `activate` export above turned out to be fragile. macOS SIP/AMFI **removes `DYLD_*` variables from the environment when a hardened-runtime binary launches a child process** — and the python.org framework Python is hardened. So even after `source activate` sets `DYLD_FALLBACK_LIBRARY_PATH`, it's gone by the time Python actually starts, and WeasyPrint can't find `libgobject`. This surfaced as `uvicorn main:app --reload` crashing in the spawned worker (`SpawnProcess-1`), but the root cause is the purge, not `--reload` specifically (the purge just doesn't fire in every launch path, e.g. some sandboxed/non-interactive ones, which is why it worked intermittently). Real fix, no `sudo`, no `DYLD`: symlink the libs WeasyPrint dlopens into **`~/lib`**, which is on dyld's built-in default fallback search path (`$HOME/lib:/usr/local/lib:/usr/lib`) that applies precisely WHEN `DYLD_FALLBACK_LIBRARY_PATH` is unset — i.e. exactly after SIP purges it. Command run once: `mkdir -p ~/lib && ln -sf /opt/homebrew/lib/{libgobject-2.0.0,libpango-1.0,libharfbuzz.0,libharfbuzz-subset.0,libfontconfig.1,libpangoft2-1.0}.dylib ~/lib/`. Those top-level libs pull their own deps via absolute Homebrew install names, so only they need linking. Verified: with `DYLD` unset, `uvicorn --reload` boots and `/health` is 200. This lives in `~/lib` (not the gitignored `.venv`), so a venv rebuild won't break it; the old `activate` line is now redundant backup. Not an issue on the Linux droplet (apt libs land in standard paths).

## v2 resume tailoring: schema, master, renderer, tailoring service (July 21, 2026)

- Resume schema (`backend/schemas/resume.py`): one Pydantic `Resume` shape shared by THREE consumers, which is the whole trick — the master file, the tailoring in/out, and the renderer all read the same shape. Sections: contact, summary (optional, the one field tailoring may rewrite), education (gpa/honors/coursework), skills (grouped category+items), experience, projects. Leadership/Activities was dropped (Lee: filler, no real content yet; not modeling hypotheticals). Dates are plain strings ("Expected May 2029", "April 2026 to Present"), deliberately NOT a real `date` (resumes use freeform ranges; the opposite of the DB's sortable `deadline`). Fields stay plain-typed (no length/number constraints) because tailoring feeds this model to structured outputs, same caveat as `ParsedJob`. Required fields (name, institution, role, project name, ...) are the fixed identity facts, so a tailoring that drops one fails validation.
- Master file `backend/data/master_resume.yaml` is the "bullet bank": it holds ALL projects and every bullet; tailoring SELECTS a subset per job at both the entry and bullet level. Built from Lee's real repos, commits, and writeups (miles/miles-app, motionsense, Life OS, the FuzzySequence org repos, and job-tracker itself). Every metric traces to a real source; unverified items are marked TODO (summary is a draft to edit, a Fuzzy quantified-impact bullet is pending, website is null). Fuzzy AI is represented as full-stack (backend API plus two frontends) per Lee's actual merged PRs, not just "frontend features". job-tracker is itself a project entry, tied to CLAUDE.md hard rule #6 (update that entry whenever the tracker gains a feature or tool).
- Renderer (the locked "format" half, which Claude never sees): WeasyPrint plus a Jinja template `backend/templates/resume.html` (structure only) and `backend/templates/resume.css` (locked styling). Font is Carlito (a free Calibri-metric clone, installed via `brew install --cask font-carlito`) to match Lee's original Calibri look; deeper-navy accent #1e3a5f; two-column aligned skills; right-aligned dates via flexbox. `backend/services/resume_render.py` exposes `render_resume_pdf(resume) -> bytes` (CSS is passed explicitly so WeasyPrint needs no base_url) and `load_master(path) -> Resume`. HTTP-ignorant like the other services.
- Tailoring (the "content" half): `backend/services/tailoring.py`, `tailor_resume(master, job_description, settings) -> Resume | None`. Model is Opus 4.8 via a new `anthropic_tailoring_model` setting (vision reserves the top model for tailoring; parsing stays on Haiku). Method is structured outputs (`client.messages.parse(output_format=Resume)`), same pattern as the parser. Prompt rules: reorder projects/experience by relevance, keep ~3 projects and 2 to 3 bullets each, rephrase into Google XYZ accomplishment bullets, rewrite the summary in 1 to 2 sentences, no em dashes (ordinary hyphens like "full-stack"/"on-device" are fine per Lee), and the hard never-invent guardrail (no new metric/technology/claim; identity facts stay fixed).
- One-page fit: the model cannot see rendered length, so a vague "fit one page" instruction produced 2 pages. Fixed two ways: (1) tightened the locked CSS spacing (line-height 1.27, smaller gaps between entries and bullets), and (2) COUNT-based caps in the prompt (at most 6 items per skills group, at most 5 tools per project, at most 2 examples inside any parenthetical, e.g. "AWS (IoT Core, Lambda)"). Lesson worth keeping: models follow item counts reliably but not character or line budgets. Result: a clean one-page resume with every skills and tools line on a single line.
- Deps added to the venv via `uv pip install`: `pyyaml`, `weasyprint==69`, `jinja2`. Preview artifacts in `backend/data/` (`master_resume.preview.pdf`, `tailored_preview.pdf`, `tailored_last.json`) are dev throwaways, not part of the app.
- STATUS: verified end-to-end by a throwaway script (sample backend/cloud internship JD to Opus to Resume to renderer to a 1-page PDF), but NOT yet wired into the app. Next steps: a `POST /resume/tailor` route (JD in, tailored Resume plus PDF out; drafts only, never auto-submit per hard rule #1), a mocked-Anthropic unit test (keep the suite off the paid API), the deferred `resume_versions` persistence table, and a frontend "Tailor for this job" button.

## v2 resume tailoring: wired into the app — routes, persistence, tests (July 21, 2026)

- Two endpoints, not one, for the tailoring flow, split along the same content-vs-format line as the services (`backend/routers/resume.py`). `POST /resume/tailor` takes JD text and returns the tailored `Resume` **JSON** (runs Opus); `POST /resume/render` takes a `Resume` and returns **PDF bytes**. Reason a single "JD in, Resume + PDF out" endpoint was rejected: one HTTP body can't cleanly be both JSON and binary, and cramming a base64 PDF into JSON would force a fresh Opus call on every re-render. Splitting means the expensive Opus call happens once and re-rendering after an edit is free; the frontend holds the Resume between calls. The tailored JSON is the reviewable draft (hard rule #1), the PDF a download of an already-reviewed draft. `/render` returns a bare `fastapi.Response` (not a model) because FastAPI JSON-encodes anything else; `Content-Disposition: attachment` makes the browser download it. A WeasyPrint failure is left to raise as a 500 (a real bug), while `tailor_resume` returning None maps to a 502 (an expected "model declined", same as the parse route).
- `resume_versions` persistence built (the table decisions deferred to "here" back in the v1 data-model note). New model `backend/models/resume_version.py`: `id` (UUID VARCHAR(36)), `application_id` (**foreign key** to `applications.id` — the first FK in the schema; SQLite does not enforce it without a pragma we haven't set, so the route guards existence instead), `resume_json` (the tailored `Resume` stored as a JSON dict), `job_description` (Text snapshot of what it targeted), `created_at`. Deliberately **no `updated_at`** — a saved version is an immutable snapshot; re-tailoring saves a NEW row (append-only history per application). No SQLAlchemy `relationship()` yet (default to less; add when a query needs to navigate). Migration `ba039539f959`.
- Save is EXPLICIT (fork 2a), never automatic. `/resume/tailor` stays stateless (drafts only); a separate `POST /resume/versions` persists a version only after you review it — matching the never-auto-submit philosophy, and keeping experimental Opus calls from littering the table. `GET /resume/versions?application_id=...` lists an application's versions newest-first. Storage-vs-API mismatch (ORM keeps `resume_json` as a dict, the API returns a validated `Resume`) is handled by an explicit `ResumeVersionRead.from_row` mapper rather than attribute aliases — one obvious place, no serialization surprises. The POST 404s if the application does not exist, which is what actually prevents an orphaned version (compensating for the unenforced FK).
- `jd_text` column added to `applications` (fork 1a, migration `189e547fa121`): the raw pasted JD, kept so tailoring can run against the real posting from a saved application. Distinct from `jd_parsed`: that is parser *output* (set on create, never touched by update); `jd_text` is parser *input* and is **re-settable via update** (you can paste a JD onto an app created by hand). Nullable Text — not queried, so a column not a JSON field, and existing rows stay valid.
- Tests keep the same "never touch external state" rule, at three levels. Service tests for `tailor_resume` mock `services.tailoring.Anthropic` (like the parser's). A route test for `/resume/tailor` uses TestClient + `app.dependency_overrides[get_settings]` and patches `routers.resume.tailor_resume`/`load_master` where they're *used*, asserting the 200 and the 502 branch — this branch matters to unit-test because, unlike the parse route, `/resume/tailor` can't be curled for free (each real call is an Opus charge). Version persistence is service-level against the in-memory `db` fixture (round-trip through the JSON column, newest-first ordering, empty list for an app with none). 19 tests green after the slice.

## v3 step 2 — Auth (DONE, July 23, 2026)

- Backend auth built as three slices: (1) `User` model + `users` table (migration `b79ea37d3021`), JWT (HS256, 7-day expiry, no refresh — deferred) + bcrypt in `services/auth.py`, config keys `jwt_secret`/`jwt_algorithm`/`access_token_expire_minutes`, and a one-off interactive `scripts/seed_user.py` (no public signup — user #1 is seeded by hand).
